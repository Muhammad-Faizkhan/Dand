## The problem

Every widget in the app sizes itself through `flutter_screenutil` — 1,795
uses of `.w`, `.h`, `.sp` and `.r` across 79 files — against a fixed
`designSize: Size(390, 844)`. ScreenUtil scales those **linearly**:

    scaleWidth = screenWidth / 390

On a phone that is exactly right. On an 820-wide iPad it means every padding,
glyph, radius and font is multiplied by **2.10**; on a 12.9" iPad by **2.63**.
The result is not a tablet layout, it is a phone screenshot blown up to poster
size.

Landscape was worse and was already reachable — `Info.plist` allows landscape
on iPhone and iPad, and the Android manifest sets no orientation lock. A phone
on its side got `scaleWidth = 844/390 = 2.16` **while** `scaleHeight =
390/844 = 0.46`: text more than doubled, vertical rhythm halved.

## The fix, in two layers

The whole app already funnels through two places, so it did not need 79 files
of edits:

* **1,795 sizing calls** all read one design size.
* **47 of 52 screens** build on `AppScaffold`; the other five are the four tab
  screens (hosted by `MainShell`) and one bottom sheet.

### Layer 1 — a tapered scale (`lib/core/utils/responsive.dart`)

`AppResponsive.uiScale` replaces linear growth with growth that stops:

```dart
final raw = screen.shortestSide / 390;
if (raw <= 1.22) return raw;            // phones: the ratio they always had
return 1.22 + (raw - 1.22) * 0.06;      // tablets: a trickle, not a doubling
```

`designSizeFor` then feeds ScreenUtil a design size computed *back* from that
scale, and `ResponsiveScreenUtil` in `main.dart` re-picks it whenever the
metrics change — rotation, iPad multitasking, a resized desktop window.

Three properties make this work:

| Property | Why it matters |
|---|---|
| The scale comes from the **shortest side** | Identical in portrait and landscape, so rotating re-flows the layout without resizing a single glyph. |
| The curve is **continuous** — 1.2390 at 599dp, 1.2391 at 600dp | No jump at the tablet threshold. |
| On anything but an upright phone, the design size makes `scaleWidth == scaleHeight` | The frame is *reproportioned* to the viewport rather than stretched, so the `Positioned`-only screens (splash, onboarding, congratulations) stay where the designer put them in any orientation — no per-screen work. |

What that produces:

| Device | Naive scale | Now | Body text | Primary button |
|---|---|---|---|---|
| iPhone 14 (390x844) | 1.000 | **1.000** | 12.0 | 56.0 |
| iPhone SE (375x667) | 0.962 | **0.962** | 11.5 | 46.4 |
| iPhone 14 landscape | 2.164 | **1.000** | 12.0 | 56.0 |
| iPad mini (744x1133) | 1.908 | **1.261** | 15.1 | 70.6 |
| iPad 10.9 (820x1180) | 2.103 | **1.273** | 15.3 | 71.3 |
| iPad Pro 12.9 (1024x1366) | 2.626 | **1.304** | 15.7 | 73.0 |

An upright phone returns the literal `Size(390, 844)`, so its rendering is
bit-for-bit what it always was.

### Layer 2 — somewhere for the freed width to go

Capping the scale leaves room over; `ContentWidth` decides what each screen
does with it.

* **`readable`** (default, 460 design units) — forms, detail pages, settings,
  auth, lists of full-width rows. Held to a measure and centred; the textured
  background stays full-bleed behind it.
* **`wide`** (780 design units) — the seven screens with card grids, which
  answer width with **columns**: 2 on a phone, 3 on an upright tablet, 4 in
  landscape and on a 12.9".
* **`full`** — the map and the dealers sheet.

`AppScaffold` applies this for all 47 screens that use it; `MainShell` applies
it per tab, so the map keeps the whole viewport while the other three centre.

The eight hard-coded `crossAxisCount: 2` grid delegates became
`responsiveGridDelegate(...)`, which derives the count from the content width
and keeps each tile's drawn aspect ratio.

**A note on the wide measure.** It was initially applied to the list screens
too (messages, notifications, orders, activity, trade matches) and to Home.
Rendering them showed the problem: those screens are full-width blocks, so
extra width just stretched every row to 993pt. They were moved back to
`readable`. `wide` now means "this screen turns width into columns" — nothing
else gets it.

## Everything else that had a fixed width

* **Bottom nav** — its tab centres are *fractions* of the bar width, so on a
  tablet the two pairs were flung into the far corners with the docked "+"
  marooned between them. The tab row is now held to a phone-like measure and
  centred under the "+"; the bar itself stays full-bleed.
* **Drawer** — `293.w`, which `uiScale` already grows to ~373 on a tablet,
  plus a 62% cap that only bites in a narrow window.
* **Dialogs and bottom sheets** — `ConfirmDialog`, `ImageSourceSheet`,
  `GetItemSheet` and the dealers sheet were edge-to-edge on a tablet; all four
  now take `AppResponsive.overlayMaxWidth`.

## Screens that could not fit landscape

Three were fixed `Column`s sized to the 844-high frame, which a tablet on its
side does not have:

* `add_item_screen` and `what_you_collect_screen` → `FillOrScroll`, which
  keeps the `Spacer` working when there is room and scrolls when there is not.
* `onboarding_screen` — each of the three pages overflowed by 146px in phone
  landscape. Each page now scrolls, with a trailing gap so the copy clears the
  dots and CTA. This was a real bug found by the new suite, not a theoretical
  one.

## Verification

`flutter analyze` proves nothing about layout, so:

**`test/responsive_test.dart`** renders all 64 platform-independent routes at
nine viewports — 576 renders — and fails on any layout exception. Plus eight
assertions on the scale curve itself (1:1 at the design frame, continuity at
the threshold, rotation invariance, uniform width/height scaling).

The suite was **validated against a planted defect**: a deliberate 9000px
overflow was inserted and confirmed to fail the run. That caught a real bug in
the test first — `pumpWidget` *updates* the tree rather than rebuilding it, so
`MaterialApp.initialRoute` was only honoured on the first iteration and every
route after the first was silently re-rendering the one before. The suite ran
in 1s and passed everything. With a per-route key it runs in 7s, and it was
that fixed version which found the onboarding overflow.

**Phone rendering is unchanged.** Three screens had their structure altered
(`add_item`, `what_you_collect`, `onboarding`), so their goldens were compared
against untouched controls:

## Goldens regenerated

Done at the end of the session, after the responsive work was verified.

* `screens_golden_test.dart` had the engine icon-font path **hard-coded at
  Flutter 3.32.0**, which would silently have rendered tofu once that cask
  moved. It now uses the same `_materialIconFont()` search
  `bottom_nav_golden_test.dart` already had.
* The harness built its own `ScreenUtilInit` with a literal `Size(390, 844)`,
  so the goldens could not have caught a regression in the responsive wrapper
  they were supposed to guard. They now render through the production
  `ResponsiveScreenUtil`. Every case here is 390x844, where
  `designSizeFor` provably returns that same size — so this changed nothing,
  which the regenerated files confirm.
* All 72 PNGs were backed up outside the project before regenerating, since
  there is no version control to fall back on.
* The regenerated files came out **within 0% of the originals in size**, and
  were spot-checked by eye: real Material icons, real fonts, nothing blank.
  That is the evidence the only difference was rasteriser drift.

## Project guardrails and the docs system

Added at the end of the session. The `/guardrails` skill referenced by the org
instructions is **not available in this session**, so its output was written
directly rather than guessing at a skill name.

**`CLAUDE.md`** (new, repo root) — ask-twice rules tuned to this stack rather
than generic ones. It leads with the fact that drove every safety decision
today:

* **There is no version control.** A `.gitignore` exists; `.git` does not.
  Nothing is recoverable — no checkout, no stash, no reflog. That makes
  ordinary operations irreversible here: `rm`, `mv`, bulk scripted rewrites
  across `lib/`, and `flutter test --update-goldens` (72 PNGs). The rule is to
  copy targets outside the project first, then get two confirmations.
* `_assets_original/` is the only copy of the source chip artwork and cannot be
  regenerated.
* `android/app/build.gradle.kts` **signs release with the debug key** — no
  release artifact until that is fixed.
* The full database/deploy rules are written out ready for when a backend
  lands. There is none today.
* Plus the house rules: `flutter analyze` + `flutter test` before done, size in
  design units, and **look at `test/failures/` before regenerating a golden**
  rather than overwriting a real layout change.

**`docs/` restructured** into the `current/` + `archive/` system, nothing
deleted:

```
docs/current/   00-INDEX.md  RESPONSIVE.md  ARCHITECTURE.md
```
