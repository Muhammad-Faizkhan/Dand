## 1. "Take Photo" on Add Item

**Reported:** the camera should open from this screen.

**What was already there.** `add_item_screen.dart` did call
`ImagePicker().pickImage(source: ImageSource.camera)` from both the scan frame
and the button, so the intent was right. Two things stopped it working and hid
the fact that it hadn't:

- `AndroidManifest.xml` declared `android.permission.CAMERA`, but nothing
  requested it at runtime and there is no `permission_handler` in the project.
  image_picker hands off to the system camera app via `ACTION_IMAGE_CAPTURE`,
  which needs no permission of ours — but *declaring* CAMERA without granting
  it makes that intent fail with a SecurityException.
- `_capture` had no error handling, so a permission refusal, a device with no
  camera, or a desktop build threw straight past the button. The tap looked
  like it did nothing at all.

**Fix.** The manifest declaration is gone, with a comment saying why so it is
not re-added casually. Picking moved behind a new `ImageSourceSheet.capture`,
which reports what actually went wrong instead of throwing:

| Platform code | What the user sees |
|---|---|
| `camera_access_denied` | "Camera access is off. Turn it on in Settings to take a photo." |
| `photo_access_denied` | "Photo access is off. Turn it on in Settings to choose an image." |
| `no_available_camera` | "No camera is available on this device." + a **Choose from gallery** action |
| `MissingPluginException` | "Taking photos is not supported on this device." + the same action |
| `already_active` | nothing — that is just a second tap while the picker is up |

A plain cancel stays silent, as it should. The gallery is only offered when the
*camera* is the thing missing; if permissions are the problem the gallery is
likely blocked too. `ImageSourceSheet.pick` routes through the same helper, so
Create Account and Edit Profile inherited the handling.

## 2. Onboarding "Skip" did nothing

**Cause.** In the screen's `Stack`, `Skip` was declared **before** the
`Positioned.fill` `PageView`. Later children paint on top and are hit-tested
first, so the full-bleed pager swallowed every tap on the button. It had always
been drawn correctly and had never been tappable.

**Fix.** `Skip` moved to the end of the `Stack` — above the pager — and given
`HitTestBehavior.opaque` so the whole 96x33 pill is the target, not just the
glyph. Tests cover Skip from the first page and the last, plus one that the
pager still swipes with the button sitting on top of it.

## 3. Chip artwork was screenshots of the app

**Reported:** the images "look like screenshots", chips cut off in the trade
grid, and item detail showing a second status bar, back arrow, heart, title and
badge underneath the real ones.

**Cause.** Every `chip_*.jpg` was a crop of a **prototype screen recording**.
`chip_bristol_wide.jpg`, for instance, is the whole item-detail screen — status
bar, back button, "Yankee Bristol", "Sturgis, SD · 125 mi away" and the "Ultra
Rare" badge all baked into the pixels. The app then drew its own chrome on top,
which is the doubling. Smaller assets carried a rarity pill or a distance chip
instead. Framing was arbitrary too: some chips on white, some on grey, some cut
off by the crop, at nine different aspect ratios — which is why tiles looked
inconsistent and the circular clips sliced chips in half.

**Fix.** The 26 files hold only **11 distinct chips**. Each was rebuilt from the
best source available:

1. The chip disc is located in every source with a Hough circle vote, taking the
   outermost well-supported ring — chips have strong inner rings that a naive
   peak locks onto.
2. For each chip, the highest-resolution source is registered against a clean
   twin of the same chip (scale + shift, scored over the disc). Diffing the two
   isolates exactly where the UI sits; those pixels are taken from the twin.
3. The handful of rarity pills no twin can answer for are listed by hand in the
   build script and patched from the same disc turned to whichever angle best
   continues the surrounding rim.
4. Everything outside the disc becomes `AppColors.surface`, so chips frame
   identically at every size and in every circular clip.

Output is 800x800, q90 4:4:4 JPEG. Chip assets went **3.8 MB → 2.6 MB**, total
bundle **5.5 MB → 4.4 MB**.

The three white plates that sat behind chip photos (`home_screen.dart`,
`add_to_trade_screen.dart`, `chip_grid_card.dart`) became `AppColors.surface`,
since the artwork now carries that colour itself.

> **Originals** are in `_assets_original/chips/` — outside `assets/`, so they
> are not bundled. The build script is not checked in; it was a one-off.

> **Still outstanding.** These are repaired screen grabs, not photographs. They
> are soft, there are only 11 of them across 26 filenames, and several file
> names do not match the chip they show (`chip_bourbon.jpg` is the Almost
> Heaven chip, `chip_bristol_wide.jpg` is Paradise, `chip_powder_keg.jpg` is
> High Stakes). Names were left alone so no screen changed what it displays.
> A tiny green trace of one badge survives on `classic` next to the "C";
> removing it costs the letter. Real product photography replaces all of this.

## 4. My Profile — camera badge and the share button

**Camera badge.** The avatar carried a red camera button that was never wired
to anything, and the photo is set on Edit Profile. Removed; the avatar is now a
plain `ClipOval`.

**Share.** `_CircleAction(icon: Icons.ios_share_rounded)` was constructed with
no `onTap` at all — decoration. It now opens the OS share sheet through
`share_plus`, carrying the profile summary and a link, with
`sharePositionOrigin` set so it does not throw on iPad, and a snackbar if the
sheet cannot open. The link is a placeholder constant until the backend issues
real profile URLs.

## 5. The avatar now propagates from Edit Profile

**Cause.** Edit Profile held the picked photo in `_EditProfileScreenState`, so
it was lost on pop and no other screen ever saw it.

**Fix.** A new `ProfileController` owns `avatarPath` and exposes an
`ImageProvider` that is the seeded asset until a photo is picked. Edit Profile
writes to it the moment the photo is chosen — not on Save — and My Profile and
the side menu both read it, so the change lands immediately without a reload.
Re-picking a file evicts the cached decode, so the same path with new content
still updates. "Remove photo" returns an empty path, which the controller reads
as a reset to the seeded asset.

Edit Profile also moved onto `ImageSourceSheet.pick`, so it offers camera as
well as gallery and inherits the error handling from section 1.

## 6. Logging out took no confirmation

**Reported:** the drawer's Log Out should ask first — confirm, or stay.

**Cause.** `side_menu.dart` called `logout()` and cleared the whole navigation
stack on the first tap, from a button that sits directly under the menu list.
There was no way back.

**Fix.** A new `ConfirmDialog` (`widgets/confirm_dialog.dart`), styled like the
app's bottom sheets — `AppColors.sheet` on a 62% scrim, r22, a title, a line of
consequence, then the two choices stacked. `ConfirmDialog.ask` returns true to
go ahead, false to back out and **null when the dialog is dismissed** by
tapping outside or going back; the drawer treats anything that is not an
explicit yes as staying signed in.

The destructive choice ("Log Out") takes the red gradient, and the safe one
("Stay signed in") is the calm secondary button placed lowest, under the thumb.
Only after a yes does the session drop and the stack reset to Login.

`ConfirmDialog` is generic on purpose — the same shape fits deleting a card,
removing a listing or cancelling an order when those need it.
